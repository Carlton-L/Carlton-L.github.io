# Demo infrastructure

How demos are built and embedded. Moved out of `CLAUDE.md` on 2026-09-26. Porting a product's real code is in `docs/DEMO_PORTING.md`; how demos fit into a case study is in `docs/CASE_STUDY_PLAYBOOK.md`.

- Infrastructure: `src/components/react/demos/_shared/` — `DemoFrame.jsx` (inner chrome: title strip, honest label, reset, fullscreen; sits flush inside a VIEW operator's body via a `.fs-viewerwrap`-style negative margin — never duplicate operator chrome), `useReplay.js` (timed event replay, scrub-safe: consumers derive state from `emitted`, never accumulate), `mockLlm.js` (canned streaming responses, seeded jitter).
- Data: `src/data/demos/` — conventions + sanitization checklist in its README.md. Synthetic or recorded-then-sanitized only, deterministic (seeded PRNG), one file per demo so any project can be password-gated later without restructuring.
- Embedding: a demo is a self-contained React island inside a VIEW operator, wrapped in `ViewSlot`. Server-rendered: `client:load` for heroes, `client:visible={{ rootMargin: '600px' }}` further down; don't use `client:only` (it leaves no markup to hold the space, so the page jumps when the island arrives). Bundle ≤300KB gz per island; homepage stays demo-free.
- Loading and pausing (2026-09-29): `src/components/ViewSlot.astro` + `src/lib/view-slot.js` + `src/styles/view-slot.css`. The slot reserves the size (the island's own server markup, or `height` / `aspect` / `phoneHeight` for vanilla content), shows the COOKING VIEWER poster, and fades the content in when it's ready: when the island inside hydrates, or on a `view:ready` event with `wait="event"` (iframes, three.js scenes). A 4s fallback starts when the slot comes near the screen. Pausing: `Patch.onScreen(el, fn)` (patch runtime) for page scripts, `_shared/useOnScreen.js` for React; one rule, within 200px of the viewport and the tab visible.
- ProductFrame (`_shared/ProductFrame.jsx`): a product running in a document of its own, scaled into the VIEW, with its phone layout below 720px. Dispatches `view:ready` when the product has drawn (its `revealOn` message, or `drawn(doc)` on the same-origin document). Talks over postMessage. DomainClaim uses it for both demos. See `docs/DEMO_PORTING.md`.
- LinkedViews (`src/components/LinkedViews.astro`): a controller op and its viewer op as one piece, with a `between` slot for anything that reads between them. One shared state (`Patch.link(field, controllerId)`), published on a port so the cables out of the controller pulse, plus the DUO corner dock. The controller element carries the link as `el.__link`. GRID uses it.
- Labels: every demo is honestly labeled via DemoFrame — `live` (real product code, synthetic data) or `recreation` (real behavior, portfolio-owned code). FAST/Engine are RECREATED-ONLY per Futurity; Futurescaper + browser extension are public (extraction allowed — `demos/futurescaper/layout.js` is the product's real algorithm, ported verbatim; its `naiveForceLayout` is portfolio-owned).
- Template: `demos/futurescaper/` + its embed in `src/pages/projects/futurescaper.astro` is the reference implementation for future demos (Engine, FAST, extension, Campus AI).
